# Korean Stickman V2.8 — голос и автоматический резерв

Подготовлена локальная версия V2.8. Она не опубликована и не заменила стабильный сайт. Архив `korean-stickman-v2.7-rollback.zip` рядом с новым архивом сохраняет предыдущую поставку для отката.

## Что изменилось

Обычный режим — «Автоматически». Ученику показываются готовность подключения, запись и обработка; названия платформ остаются в настройках и отчёте. Ручные режимы Render, Vercel и Netlify отключают автоматическое переключение. Отдельный диагностический тест V2.7 также отправляет запись только явно выбранному серверу.

Адреса заданы в одном реестре `src/stt-servers.js` и в сборке Pages:

- Render: https://korean-stickman.onrender.com
- Vercel: https://korean-stickman.vercel.app
- Netlify: https://incandescent-lollipop-01828a.netlify.app

Игровые уровни, внешний вид персонажа, предметы, навигация, интерпретаторы и сохранение мира не изменялись. Серверная бизнес-логика STT тоже не менялась. Клиент V2.8 совместим с уже развёрнутым API версии `1` и серверной сборкой `2.7.0`: наличие этого номера в `/health` ожидаемо и не означает, что интерфейс остался V2.7.

## Выбор подключения

При открытии выполняется одна параллельная проверка всех настроенных серверов. Проверяются HTTP, JSON, `ok`, `configured`, версия API `1`, версия сборки и идентичность платформы. `/health` не обращается к Groq.

Render выбирается сразу, если готов. Резервные результаты ожидают его не более 2,5 секунды. После этого используется готовый резерв, без ожидания медленного Render. Если ни одного пригодного ответа ещё нет, выбор ограничен 8 секундами. При подтверждённом отказе предпочтительных серверов резерв может быть выбран раньше. Поздние ответы продолжают обновлять таблицу диагностики, но выбранный сервер не заменяют.

Обычный порядок — Render, Vercel, Netlify. На следующем запуске учитывается последний сервер с успешным STT: при недоступном Render проверенный и снова готовый резерв получает предпочтение. Render сохраняет приоритет при новой проверке. Успешный сервер сохраняется отдельно в localStorage только как идентификатор; аудио туда не попадает.

Перед каждой фразой повторных health-запросов нет. Новая проверка возможна по кнопке или при возвращении во вкладку после десяти минут простоя. Во время записи, обработки и игровых операций проверки/переключения из настроек блокируются. Если первоначальный выбор завершился во время текстовой игровой операции, применение выбора откладывается до её окончания. Постоянного опроса и heartbeat нет.

На localhost Render означает локальный Node API: запуск остаётся `npm ci`, `npm run dev`, http://localhost:5173/. В диагностике виден фактический адрес локальной проверки. Публичные резервы могут блокировать запросы из localhost своим CORS; это не мешает локальному Render. На GitHub Pages все проверки идут к публичным backend.

## Отправка и резервные попытки

Запись по-прежнему начинается первым нажатием и завершается вторым. Тишина не завершает запись и не удаляется из файла. Аудио последовательно отправляется активному серверу, затем при техническом сбое — резервам. Несколько STT-запросов одной операции одновременно не запускаются со стороны клиента.

Переключение разрешено для сетевых ошибок, тайм-аутов, некорректного контракта ответа и подходящих HTTP 500/502/503/504. Неизвестная команда, сомнительная или пустая транскрипция, ошибка игровой логики, доступ к микрофону, формат и прочая валидация переключение не запускают. Неверный ключ Groq и любой HTTP 429 также останавливают автоматические попытки. Для 429 выбран консервативный вариант: не предполагать, что лимит независим на разных платформах.

На одну сохранённую запись разрешены максимум две **автоматические резервные отправки**. Этот бюджет не сбрасывается кнопкой повторной отправки. Если он уже исчерпан, явное «Повторить отправку» делает только одну запрошенную пользователем попытку. Новая запись получает новый бюджет. Запрос ограничен 30 секундами на одну сетевую попытку; суммарное ожидание трёх попыток ограничено примерно 90 секундами плюс небольшие накладные расходы.

Перед каждой отправкой проверяются исходные размер и длительность: Render — 20 МиБ; Vercel/Netlify — 4 000 000 байт и пять минут записи. Первичная ошибка валидации не запускает резерв. После технического сбоя неподходящие резервы пропускаются. Файл не обрезается и не перекодируется. При отсутствии подходящего резерва показывается объяснение, файл сохраняется для явной попытки или новой записи.

Каждая запись получает уникальный клиентский идентификатор. Резервные и ручные повторные отправки используют тот же Blob, язык и идентификатор. Игра получает только первый принятый результат; сетевой обработчик вообще не исполняет игровых команд. Отмена, новая запись и переход на другой уровень делают старую сессию неактуальной. Запоздалые ответы не применяются.

Аудио остаётся только в памяти вкладки до успешного STT, отмены/удаления, новой записи или закрытия вкладки. После сбоя доступны «Повторить отправку» и «Записать заново». В диагностическом режиме сохранено намеренное удержание образца для ручного сравнения серверов; оно не выполняет игровые действия.

Клиентский идентификатор предотвращает повторное применение в игре, но не гарантирует отсутствие повторного расхода Groq: предыдущий сервер мог уже принять запись до сетевого тайм-аута. Серверной дедупликации и новой базы данных нет.

## Кнопка и индикатор звука

Готовность: розово-красный микрофон, «Нажми и скажи», короткая инструкция. Запись: насыщенный зелёный цвет, квадрат «Стоп», «Нажми, чтобы завершить», таймер и полоски звука. При обработке запись и полоски остановлены, кнопка заблокирована, показано «Распознаём речь…»; при резервной отправке — «Пробуем другое подключение…».

Полоски используют RMS из существующего AnalyserNode и того же MediaStream. Амплитуда сглаживается; во время тишины стремится к минимуму. После пяти секунд низкого уровня появляется ненавязчивая подсказка. Никакой оценки произношения по громкости нет. Второй микрофонный поток не создаётся. Таймер анализа, дорожки и AudioContext освобождаются при завершении, ошибке или отмене.

Если Web Audio/визуализация недоступны, MediaRecorder продолжает работать. В таком браузере локальную проверку акустической тишины провести нельзя: остаются проверки размера и длительности, затем проверка STT. Учтено `prefers-reduced-motion`; состояние различимо по значку и тексту, а не только цвету.

## Файлы и публикация

Новые клиентские модули: `src/stt-connection.js`, `src/stt-failover.js`. Изменены `src/stt-servers.js`, `src/routed-stt.js`, `src/stt-client.js`, `src/speech.js`, `src/voice-diagnostics.js`, `src/main.js`, `src/style.css`, `index.html`, `scripts/build-pages.mjs`, `.github/workflows/pages.yml`, `package.json`, `package-lock.json`, `README.md`. Добавлены тесты V2.8; прежние тесты реестра и отказа визуализации приведены к новым требованиям. Добавлены этот отчёт и два подписанных скриншота.

Backend и его ключи для V2.8 менять не требуется. Сначала можно проверить frontend в отдельном репозитории Pages, не заменяющем стабильный `korean-stickman`. Если тестовый репозиторий находится под тем же `averanges.github.io`, CORS уже подходит, но localStorage общий для источника: используйте отдельный профиль браузера или приватную вкладку, чтобы тестирование не изменяло сохранение стабильной игры.

Для публикации frontend:

1. Загрузить исходники подготовленной игры в выбранный репозиторий. Не загружать `.env`, work, rollback ZIP или другие архивы.
2. Pages → Source: GitHub Actions. Workflow `Publish frontend to GitHub Pages` уже собирает только публичный `dist`.
3. Публичные Repository Variables при необходимости: `API_BASE_URL`, `VERCEL_API_BASE_URL`, `NETLIFY_API_BASE_URL`. Их текущие значения уже заданы по умолчанию в сборке и workflow. Ключ Groq в Pages не добавлять.
4. Для самостоятельной сборки: задать `API_BASE_URL=https://korean-stickman.onrender.com`, затем `npm ci`, `npm run build:pages`. Опубликовать содержимое `dist` выбранным способом Pages.
5. После тестовой публикации проверить микрофон на настоящих компьютере и телефоне, длительную паузу и копируемый отчёт. Только затем заменять стабильный frontend.

Render/Netlify/Vercel продолжают обслуживать свои прежние API. Новые фоновые службы, платные сервисы и серверная система хранения не добавлены. Публикацию, push и изменение облачных настроек Codex не выполнял.

Для отката восстановить файлы из `korean-stickman-v2.7-rollback.zip` или предыдущую ревизию GitHub и повторно опубликовать frontend. Серверный API версии `1` остаётся совместимым.
